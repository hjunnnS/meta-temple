# I08 #11 — 서버·데이터·운영 구조 제안

상태: 설계 초안. 호스팅·DB·예산·담당 승인 전이며 서버 구현은 M2 I68부터.

## 구조와 책임

브라우저/앱(UI·3D) → HTTPS API(인증·공개 범위·거래 권한) → 관계형 DB(슬롯/예약/주문/설치 원본).
실시간 게이트웨이는 방문 세션·좌표·동작 및 권리 변경 알림을 제공한다. 권리 원본 DB를 대신하지 않는다. 이벤트 발행은 outbox + 고유 eventId + aggregateVersion 방식 제안. 클라이언트 누락은 원본 조회로 수렴.

기술 후보: Node/TypeScript 서버, PostgreSQL의 제약조건/트랜잭션으로 슬롯 원자성을 보장하는 방향. 제품·배포 형태·구체 스키마는 승인 후 구현한다. 예약을 프로세스 메모리에만 저장하지 않는다. P04 동시 선택 후보 수집과 승자 선정은 모든 서버 인스턴스가 같은 상태를 보도록 한다.

## 단계 경계

M1: 인터페이스·상태 계약·대표 장면과 측정 기능. API가 실제로 동작한다고 주장하지 않음.
M2 I68: 실제 슬롯 조회 + 샘플 설치. 샘플 계정/권리/슬롯 namespace 및 검수 환경 격리. I04는 독립 시험 세션의 좌표·애니메이션, 운영 로그인과 분리.
M3: 실제 인증·거래·소유권·운영 채널. M2 샘플 권리를 실제 구매 권리로 이전하지 않는다.

## 환경·비밀값·관측

local / staging / production 분리. 클라이언트 빌드에는 공개 설정만. 비밀키·DB 연결·결제 서명키는 서버의 환경별 비밀 저장소에 둔다. 모든 민감 원문/토큰 로그 금지. 감사 로그는 운영 조작 주체·대상·사유·전후 상태를 기록하며 P07 보존 정책에 종속.

P12 승인: 판매 용량, 동시 접속·채널 정원, 상태 전파 지연, 단절 기준, 재조회 주기. 20세션 시험은 전체 서비스 용량 계약 아님.
P13 승인: 호스팅·DB·월 예산·운영 담당·백업 주기·RTO/RPO·알림 임계치. 아직 유료 리소스 생성 없음.
장애: 거래 결과 불명 시 슬롯 잠금 유지 → 제공자 재조회 → 권리 대사. 서비스 복구는 백업 복원 후 원거래·설치·슬롯 대조. 배포 롤백은 스키마 호환 여부 확인 후 실행. 일반 운영자가 DB를 직접 수정해 환불 처리하지 않는다.

## M2에 전달할 웹 검증 계약

#72의 읽기 응답은 layoutVersion과 schemaVersion을 포함한다. 좌표는 현재 배치의 미터 단위 [x,y,z], +Y 위, +Z 북쪽, 회전은 라디안이다. 설치가 없는 슬롯은 sampleInstallation을 생략한다. 있으면 installationId, ownerId, productKind, slotId를 포함한다. 내 소유 표시는 시험 세션에 연결된 ownerId로 계산한다. 모르는 버전이나 중복 슬롯 ID는 장면에 부분 반영하지 않고 오류를 표시한다. 동일 버전 재조회는 슬롯 ID와 기존 설치 좌표를 보존한다.

#52의 두 브라우저는 서로 다른 임시 sessionId로 같은 test 채널에 입장한다. 입장 시 참여자 목록과 위치를 받고 이후 sessionId, sequence, position, yaw, animation을 교환한다. 세션별 이전 sequence는 무시한다. 연결 종료는 참여자 제거, 재입장은 새 세션과 전체 스냅샷 조회로 확인한다. M2 수락 시 두 창에서 서로의 이동과 퇴장, 재접속을 모두 기록한다.

#32부터 인증된 계정과 운영 DB를 연결한다. 임시 sessionId는 구매 권리가 아니다. P12 운영 정원은 #54·#68, P13 인프라 예산·담당·복구 목표는 #60·#61·#65의 선행 결정이다.

## 검수 환경 운영안

M1은 기존 GitHub Actions와 로컬 정적 빌드를 사용한다. M2 샘플 서버 설계 기준은 Node/TypeScript API와 PostgreSQL이며 같은 DB 안에서도 운영 계정·주문과 시험 세션을 섞지 않는다. 스테이징 빌드 버전·오류율·API 지연·활성 채널과 동기화 단절 횟수를 관측하고, 서비스 키는 서버에만 둔다. 운영 배포에서 결제 확인 지연·설치 복구 대기·환불 실패는 별도 알림과 담당 대사 대상으로 기록한다. 배포 실패 시 이전 호환 빌드로 복귀하고 DB 변경은 이전 버전 읽기를 유지하는 확장→이전→정리 순으로 적용한다. 실제 월 예산, 백업 주기, 복구 시간과 허용 데이터 손실은 서비스 책임자 결정 후 기록한다.

[검수용 응답 예시](m2-sample-contract.json)에는 실제 장면에 존재하는 설치 슬롯 하나, 빈 슬롯 하나, 별도 시험 세션의 입장·이동·퇴장을 담았다. 예시는 계약을 설명하는 파일이다. #72와 #52가 이 형식으로 실제 서버 왕복을 검증한다.

2026-11-08 P13 사용자 승인. M2 검수 서버는 이 Mac의 루프백 주소로 제한한다. npm run review로 실행하고 http://127.0.0.1:4320 에서 확인한다. #24에서 승인한 다섯 아이템의 배치 규격은 layout-web-014이다. 맵과 검수 서버는 src/contracts.ts의 좌표·방향·종류를 함께 사용한다. server/review-layout.mjs가 각 구역의 샘플 설치 상태를 제공한다. server/sample-slots.json은 #72에서 사용한 이전 버전의 두 자리 예시다. 검수 화면의 ‘슬롯 다시 조회’로 다섯 구역을 함께 갱신한다. 레이아웃이나 응답 구조 변경 시 버전을 올려 클라이언트 검사와 함께 변경한다. 일반 배포 빌드에는 검수 API를 제공하지 않는다.

## 계정 없이 실행하는 단일 서버 후보

`npm run candidate:local`은 Node 24와 PostgreSQL 17이 있는 이 Mac에서 서비스용 웹을 빌드하고 http://127.0.0.1:4342 에서 제공한다. 브라우저의 3D 렌더링, 같은 주소의 서비스 API, PostgreSQL 및 주기적인 주문 복구·개인정보 처리·백업으로 구성한다. Node 서버는 빌드 결과만 제공하며 Vite는 빌드 단계에 사용한다. 방문 채널과 수행 상태는 서버 프로세스 메모리에, 계정·주문·설치 내역은 DB에 보관한다.

기본 미리보기(4340), 자동 검수(4341), 이 후보(4342)는 별도 프로세스다. 후보의 DB는 `.m3-local/standalone/socket`의 54840번 `temple_candidate`이고 웹·우편·백업은 같은 상태 디렉터리의 web, mail, backups에 보관한다. 브라우저 접속은 루프백으로 제한한다. 종료는 실행 터미널에서 Ctrl+C, DB까지 정지하려면 `pg_ctl -D .m3-local/standalone/db -m fast stop`을 사용한다.

이미 준비한 빌드와 로컬 DB를 실행할 때는 `node server/candidate.mjs`에 SASA_STATE_DIR(web/index.html 포함), SASA_DB_HOST(로컬 소켓 또는 루프백), SASA_DB_PORT, SASA_DB_NAME, SASA_DB_USER, SASA_HTTP_PORT를 지정한다. 백업·복원 CLI에도 같은 DB와 상태 경로를 지정한다. /health/live는 프로세스 응답, /health/ready는 실제 DB 질의 성공 여부를 알려 준다. `npm run check:local`은 4341에서 같은 서버 실행 파일로 별도의 시험 데이터를 검수한다.

AWS 이전 시에는 서버·DB 위치와 예산, 외부 백업 보관, HTTPS 도메인과 인증·결제 제공자를 먼저 확정한다. 이 로컬 실행 설정은 단일 프로세스의 시험 거래 전용이다.
