# I08 #11 — 서버·데이터·운영 구조 제안

상태: 설계 초안. 호스팅·DB·예산·담당 승인 전이며 서버 구현은 M2 I68부터.

## 구조와 책임

브라우저/앱(UI·3D) → HTTPS API(인증·공개 범위·거래 권한) → 관계형 DB(슬롯/예약/주문/설치 원본).
실시간 게이트웨이는 방문 세션·좌표·동작 및 권리 변경 알림을 제공한다. 권리 원본 DB를 대신하지 않는다. 이벤트 발행은 outbox + 고유 eventId + aggregateVersion 방식 제안. 클라이언트 누락은 원본 조회로 수렴.

기술 후보: Node/TypeScript 서버, PostgreSQL의 제약조건/트랜잭션으로 슬롯 원자성을 보장하는 방향. 제품·배포 형태·구체 스키마는 승인 후 구현한다. 예약을 프로세스 메모리에만 저장하지 않는다. P04 동시 선택 후보 수집과 승자 선정은 모든 서버 인스턴스가 같은 상태를 보도록 한다.

## 단계 경계

M1: 인터페이스·상태 계약·대표 장면과 측정 기능. API가 실제로 동작한다고 주장하지 않음.
M2 I68: 실제 슬롯 조회 + 샘플 설치. 샘플 계정/권리/슬롯 namespace 및 검수 환경 격리. I04는 독립 시험 세션의 좌표·애니메이션, 운영 로그인과 분리.
M3: 실제 인증·거래·소유권·운영 채널. M2 샘플 권리를 실제 구매 권리로 이전하지 않는다.

## 환경·비밀값·관측

local / staging / production 분리. 클라이언트 빌드에는 공개 설정만. 비밀키·DB 연결·결제 서명키는 서버의 환경별 비밀 저장소에 둔다. 모든 민감 원문/토큰 로그 금지. 감사 로그는 운영 조작 주체·대상·사유·전후 상태를 기록하며 P07 보존 정책에 종속.

P12 승인: 판매 용량, 동시 접속·채널 정원, 상태 전파 지연, 단절 기준, 재조회 주기. 20세션 시험은 전체 서비스 용량 계약 아님.
P13 승인: 호스팅·DB·월 예산·운영 담당·백업 주기·RTO/RPO·알림 임계치. 아직 유료 리소스 생성 없음.
장애: 거래 결과 불명 시 슬롯 잠금 유지 → 제공자 재조회 → 권리 대사. 서비스 복구는 백업 복원 후 원거래·설치·슬롯 대조. 배포 롤백은 스키마 호환 여부 확인 후 실행. 일반 운영자가 DB를 직접 수정해 환불 처리하지 않는다.
