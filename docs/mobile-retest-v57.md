# v57 모바일 재검수

2026-11-20. 사용자의 ‘다시 테스트’ 요청에 따라 공개 v57을 그대로 검사한다. 기존 M4 / Epic #1·#4·#74 / Implementation #64·#77의 검수 후속이며, 예상 검수 S와 연속 접속 대기를 분리한다. 새 Issue·Milestone을 만들거나 승인 상태를 바꾸지 않는다. 제품 코드·가격·결제·공개 배포는 이번 재검수에서 변경하지 않는다.

## 환경과 범위

Mac의 Playwright WebKit 및 설치 Chrome에서 iPhone 14 Pro 화면 크기·터치·기기 배율을 모의한다. 이것은 실제 iPhone 14 Pro, 실제 iOS Safari 프로세스의 메모리 한도나 온도 센서 검사가 아니다. 공개 URL의 최신 버전 57을 확인하고 그 주소로 검수한다.

- 두 엔진에서 연속 입장 3회씩, 입장 전 3D 미생성, 기본 가벼움/20fps 확인.
- 두 엔진에서 지도 20회 열기·닫기·회전·번호/장소 선택, 메뉴 닫기·뒤로 버튼 표시, 키보드 포커스, 일정 KST 제거 확인.
- 별도 두 엔진의 동일 세션에서 지도 빠른 열기 100회씩 후 최소 5분간 걷기 10초→지도 10초→전체 메뉴 10초를 10회 반복한다. 이 실행은 동작 완화 조건이다.
- WebKit에서 동작 완화를 끈 기본 애니메이션 조건도 별도 5분 연속 검사한다. 앞선 동작 완화 검사 결과를 일반 애니메이션 검증으로 대신하지 않는다.
- 검사 중 페이지 재탐색·브라우저 page crash·WebGL 연결 손실·입장 화면 재등장과 장면 메시 수를 기록한다. Chrome은 강제 GC 후 JS heap 사용량의 전후를 기록한다. 이 값은 iPhone의 전체 RAM/GPU 메모리나 최고 메모리 사용량을 뜻하지 않으며, 전후 값만으로 누수가 완전히 없다고 판정하지 않는다.

## 해석 원칙

지도 반복 검사에서 재로딩이 없더라도 사용자 기기의 재로딩을 해결했다고 단정하지 않는다. 모바일 20fps와 메뉴 중 0프레임 확인은 렌더링 동작 검사이며 발열 감소율 검사가 아니다. WebKit의 기존 Colyseus 생성자 fallback 진단은 별도 sdkDiagnostics로 보존하고 다른 페이지 오류와 구분한다. 실제 iPhone에서 사용자가 보고한 언어 선택·연꽃 입장 화면 재등장 및 발열은 실기기 재검증이 필요하다.

원시 결과는 `evidence/mobile-retest/`, 연속 검사 코드는 `scripts/check-mobile-soak.mjs`에 있다. 모든 브라우저는 검수 종료 시 닫는다.

## 최종 결과: 전체 통과 아님

1. 두 엔진의 연속 입장 3회씩과 지도 20회·회전·버튼 테두리·KST 표시 기본 검사는 통과했다. WebKit 첫 입장은 이 실행에서 약 5.4초, Chrome 약 4.0초였으나 Mac 측정이며 휴대폰 성능 보장이 아니다.
2. 동작 완화 조건의 WebKit은 지도 빠른 열기 100회와 약 309초 연속 검사를 통과했다. 재로딩·page crash·WebGL 손실 0회. 걷기 약 20fps, 지도/메뉴 0프레임이었다.
3. 동작 완화 조건의 Chrome도 100회 지도 열기와 약 310초의 모든 조작 단계를 마쳤고 재로딩·page crash·WebGL 손실은 0회였다. 다만 마지막 자동 판정에서 전체 메시 수 2,921→2,860을 실패로 처리했다. 전체 메시 수는 공유 방문객/가상 방문객 수에 따라 바뀌므로 이 차이를 곧바로 메모리 누수나 제품 실패로 판정하지 않는다. 원시 실패 결과를 보존하고 이후 검사 코드는 정적인 architecture 메시 수로 비교하도록 수정했다. 수정된 기준으로 동일 5분 Chrome 경로를 다시 실행하지 않았으므로 원래 자동 검사를 전체 통과로 고쳐 쓰지 않는다. 강제 GC 후 Chrome JS heap은 345,624,336→345,725,556바이트였으며 최고 메모리·전체 GPU 메모리·실제 iPhone 메모리 검사가 아니다.
4. **일반 애니메이션 조건의 WebKit에서 새 터치 차단을 재현했다.** 첫 걷기→지도→메뉴 흐름을 마친 뒤 다음 지도 버튼이 보이고 활성 상태인데도 실제 터치 hit target이 HTML이 되어 입력이 막혔다. 키보드 이동 조건으로 재확인했고 화면 조이스틱을 pointer drag로 조작하는 조건에서도 같은 상태가 발생했다. 조이스틱 드래그는 Playwright의 trusted mouse pointer로 조작했고 지도/메뉴는 touchscreen.tap을 사용했다. 이것을 실제 iPhone의 물리 터치 검사로 표시하지 않는다.
5. 차단 시 entry overlay 없음, app.inert=false, 열린 dialog와 :modal 목록 없음, 스크롤/visualViewport offset 0이었다. 따라서 언어 선택 화면 재등장이나 단순히 열린 대화상자가 덮은 상태와 구분한다. 포커스만 해제해도 hit target은 HTML에 머물렀다. 제품 상호작용·WebKit hit testing·검사 환경 중 어디에 원인이 있는지는 아직 확정하지 못했다. 일반 애니메이션이 원인이라고 단정하지 않으며 재현 조건으로만 기록한다.
6. 사용자 보고의 언어 선택·연꽃 화면 재등장은 이번 검사에서 재현하지 못했다. 실제 iPhone 발열도 측정하지 못했다. 새 터치 차단이 있어 모바일 안정성을 전체 통과로 판정하지 않는다.

증빙: `normal-reproduction/webkit-result.json`, `normal-stick/webkit-result.json`, `focus-probe/webkit-result.json` 및 각 failure.jpg. 초기에 계획한 일반 애니메이션 5분 검사는 위 차단 때문에 1회 흐름 뒤 중단됐으며 5분 통과로 표시하지 않는다. 공개 제품 소스와 v57 게시본은 수정하지 않았다.

## 추가 모바일 최적화 점검

사용자의 ‘모바일 최적화할 부분과 발열을 다시 확인’ 요청으로 v57을 추가 점검했다. 제품 소스·기본 설정·게시본은 변경하지 않았다. 검사 브라우저에서만 효과와 모델을 일시 해제해 비교하고 닫아 원상 복원했다. 기존 M4 / Epic #1·#4·#74 / Implementation #64·#77의 검수 및 보완 후보이며 새 Issue를 등록하거나 구현 승인으로 간주하지 않는다.

### 검증 범위와 앞선 판정의 보완

- 강제 화면 크기 변경을 제외한, iPhone 14 Pro 프리셋의 기본 viewport와 일반 애니메이션·화면 조이스틱 pointer 조작 조건에서 WebKit 310.065초/10회 흐름을 완료했다. 재로딩·page crash·WebGL 손실 0회, 렌더링은 이동 약 20fps/지도·메뉴 0프레임, 정적 건물 메시 수 동일이었다. 실제 iPhone 검사로 표시하지 않는다.
- 앞선 일반 애니메이션 차단 재현에는 입장 후 viewport 높이를 프리셋의 약 660px에서 852px로 강제 변경한 조건이 섞여 있었다. 이번 분리 검사에서 화면 높이를 유지한 경우는 통과했고, 강제 변경 후에는 상단 햄버거는 터치를 받지만 하단 지도 버튼의 hit target이 HTML이 되는 경우를 확인했다. 따라서 ‘일반 애니메이션이면 모든 메뉴가 막힌다’로 일반화하지 않는다.
- 검사 환경에서 innerHeight/visualViewport.height/100dvh 값이 서로 달라지는 것을 사찰 코드와 WebGL이 없는 작은 fixture에서도 확인했다. fixture 자체에서는 터치 차단을 재현하지 못했다. 제품 하단 배치와 검사 환경의 상호작용을 분리해야 하며, 실제 Safari의 주소창·회전 상황과 동일한 원인이라고 확정하지 않는다. 배경 렌더링을 계속 켜도 차단이 발생할 수 있어 절전 일시 정지만의 문제로 단정하지 않는다. 단순한 root 높이·canvas 숨김·CSS isolation·중앙 정렬 transform 제거·dialog 재설정은 해당 실패 상태를 복구하지 못했다.

### 측정으로 확인한 최적화 후보

1. **하단 메뉴·조작의 실제 표시 영역 기준 통일 (#64 후속, 먼저 재현 분리).** viewport/visual viewport/dvh가 달라지거나 주소창·가상 키보드·회전이 생길 때 메뉴와 터치 좌표를 함께 검수해야 한다. 기존 터치 차단은 여전히 이 조건에서 미해결이며 물리 기기 검증이 필요하다.
2. **가상 방문객의 거리별 모델·동작 계산 및 공용 자원 재사용 (#77 후속).** 가까운 NPC의 기존 모습과 행동, 20명 자동 조절 의도는 유지한다. 낮 중앙마당의 대조 실험에서 기본 마지막 표본은 프레임당 약 629.5 그리기 호출, 가상 방문객 렌더링과 행동을 시험용으로 모두 끄면 421.5였다. 약 33% 차이는 모든 AI를 제거한 실험 상한이며 LOD 최적화로 그만큼 개선된다는 예측이나 적용 결과가 아니다. 정밀 표현을 가까운 대상에 집중하는 근거다.
3. **초기 모델 중복 생성 제거와 정적 구역 분할 (#77 후속).** 현재 refinedVisitor는 legacyVisitorMesh를 먼저 만들고 그 메시를 폐기한 뒤 새 외형을 만든다. 표시하지 않을 구형 geometry를 생성하지 않는 rig 분리, 캐릭터 공통 부품 geometry/material 공유가 가능하다. 사찰 정적 건물은 약 2,585,130 정점을 유지한다. 모든 부분을 처음부터 생성하는 대신 미리 만든 자산·구역별 준비·공간별 병합/가시성 처리를 검토한다. 현재 건물 병합은 주로 material/vertex 형식/정점 수 기준으로, 서로 먼 장소가 같은 batch에 들어갈 수 있다. 공간 분할의 실제 이득은 별도 측정이 필요하다.
4. **그림자와 개인 공간 갱신 주기 (#77 후속).** 낮 중앙마당에서 그림자를 시험용으로 끄면 약 629.5→539 호출이었다. 제거가 아니라 가까운 영역·고정 구조물의 재계산을 줄이는 방향이 후보다. 공개 사찰의 모바일 저품질 그림자는 512px/6프레임 갱신이지만 개인방은 512px/매 프레임 갱신이었다. 개인방 정적 가구·풍경 그림자의 갱신을 줄일 여지가 있다. PC 품질 유지가 조건이다.
5. **장시간 프레임 지연에 따른 적응형 절전 (#77 후속, 후순위).** 현재 기본은 고정 20fps다. 지속적인 프레임 지연과 사용자 움직임/수행 상태를 보고 모바일 렌더 해상도·부가 효과 빈도를 조절하는 방식이 후보다. 브라우저에서 실제 기기 온도를 읽었다고 표시하지 않으며, 절하기·걷기·가까운 방문객 동작의 시간 진행을 유지해야 한다.

연등 번짐은 중앙마당에서 프레임당 약 8 호출 차이였고 CPU 측정은 흔들렸다. GPU 시간·전력은 측정하지 않았으므로 번짐을 끄면 발열이 크게 줄어든다고 단정하지 않는다. 연못 반사는 이 카메라에서 호출 차이가 없었고, 해당 장면 밖의 효과까지 일반화하지 않는다. 낮/밤 표본에서 활성 메시 약 530~600개, 프레임당 약 630~680 호출이 관찰돼 작은 출력 해상도와 20fps만으로 모바일 부하가 충분히 작다고 볼 수 없다.

### 개인 공간과 자원 유지

WebKit 모바일 기본 화면에서 연못→도심 야경→한강뷰→단풍 산→설경→연못을 검사했다. 개인방 메시 수는 87→139→152→104→107→87, material 수는 34→57→68→49→45→34로 원래 수준에 돌아왔다. 퇴장 후 engine.scenes는 2→1로 복구했다. 이 경로의 메시/material 수가 계속 쌓이는 현상은 관찰하지 못했으나 전체 메모리 누수 부재의 증명은 아니다. 개인방 입장 중 공개 사찰 약 2,860 메시가 보존돼 빠른 복귀와 메모리 절감 사이의 정책 검토 여지도 있다.

### 측정 제한 및 원시 결과

데이터: `evidence/mobile-audit/workload-corrected`, `native-viewport-soak`, `private`, `hit*`, `viewport-fixture*`. 첫 workload 실행은 엔진의 누적 draw counter를 프레임 값으로 읽은 오류가 있어 원시 `workload/`를 진단용으로 보존하고, 최종 판단에는 프레임별 증가량으로 바로잡은 `workload-corrected/`만 사용했다. CPU 수치는 scene before/after 구간의 main-thread 처리 시간이며 GPU 시간·전체 프레임 시간·기기 전력이나 온도가 아니다. 다른 검수 세션의 참가/퇴장으로 동적 방문객 수가 달라진 표본이 있어, 카메라와 활성 메시 수가 같은 마지막 기본 표본을 중심으로 비교했다.

실제 iPhone 14 Pro의 온도와 강제 재로딩은 이번에도 측정·재현하지 못했다. 발열 해결 판정은 보류한다. 우선순위는 화면 영역/터치 안정성 분리, NPC 표현과 초기 생성 경량화, 정적 구역 처리, 그림자, 적응형 절전이다.
