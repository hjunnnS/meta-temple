# 모바일 최적화 5개 항목 구현 및 검수

2026-11-20. 기존 M4 / Epic #1·#4·#74 / Implementation #64·#77 후속으로 사용자가 승인한 순서대로 구현했다. 기존 Issue 번호·승인 상태를 유지하며 새 Issue나 목표 날짜를 만들지 않았다. 가격·결제는 변경하지 않았다.

## 적용 내용

1. Safari의 동적 화면 높이·너비와 visualViewport를 함께 반영한다. 화면 회전, 주소창 변화, 키보드, 축소된 화면에서 캔버스와 터치 버튼이 동일한 영역을 사용한다.
2. 모바일에서 가까운 방문객의 기존 외형을 유지하고 중거리·원거리의 작은 장식과 자세 갱신 빈도를 줄인다. 이동·휴식·참배 루프와 인원 자동 조절을 유지하며, 한 프레임에 경로를 한 개씩 계산한다.
3. 표시하지 않을 구형 캐릭터 geometry의 중복 생성을 제거하고 동일한 둥근 부품 geometry를 공유한다. 조밀한 건축 묶음은 건물 기준으로 나눠 가시성 처리가 가능하게 했다. 정적 건축 정점 2,585,130개를 유지한다. 모든 지역을 나중에 불러오는 방식으로 바꾼 것은 아니며 초기 정적 생성은 남아 있다.
4. 모바일 그림자 대상에서 멀리 떨어진 건축 묶음을 제외하고 개인방 그림자를 매 프레임 대신 4프레임 간격으로 갱신한다. PC 그림자 설정은 유지한다.
5. 모바일에서 45초간 입력이 없으면 기본 20fps를 15fps로 줄이고 조작하면 복귀한다. 수행 중에는 방치 절전을 적용하지 않는다. 지속적인 프레임 지연에는 해상도·그림자·반사·번짐 부하를 단계적으로 줄이고 안정되면 복원한다. 사용자 품질 선택은 보존한다. 온도를 감지하는 기능은 아니다.

## 검증

- 정식 저장소 단위 검사 129개, 체험판 68개 및 두 빌드 통과. 두 저장소 diff 공백 검사 통과.
- 공개 v57 대비 PC 건축·지형·캐릭터의 geometry, 색상, 부착 상태 비교 통과. PC 그림자 4096 설정 유지.
- Mac WebKit·Chrome에서 iPhone 14 Pro 화면·터치를 모의해 4개 화면 크기, 실제 터치 hit target, 조이스틱, 핀치, 메뉴, 회전, 개인방 이동 검사 통과.
- 가까운 방문객 52개 부품이 원거리에서 27개로 줄고 다시 접근하면 52개로 복원된다. 20명 기준 인원 정책 유지. 공통 셔츠 geometry는 한 개를 공유하며 구형 재킷 생성은 0개다.
- 기본 애니메이션 WebKit 약 310초 연속 걷기·지도·메뉴 검사에서 재로딩·page crash·WebGL 손실 0회. 걷기 20fps, 지도·메뉴 0프레임.
- 방치 15fps, 입력 복귀 20fps, 명상 중 20fps 확인. 시험용 프레임 지연을 주입해 적응 단계 2까지 내려간 뒤 품질 재선택으로 복원되는 경로 확인.
- 동일한 1명 실제 방문객/19명 가상 방문객 조건의 Chrome 강제 GC 후 JS heap은 343,741,764→302,316,184바이트(약 12% 감소), geometry 수는 2,858→1,440개였다. 전체 RAM·GPU 메모리·최고 메모리 사용량 측정은 아니다.
- 최종 WebKit 중앙마당 표본은 낮 약 543회, 밤 579회 그리기 호출이었다. 기존 감사 표본은 약 630~680회였다. 인원·행동·카메라 조건 차이가 있어 이 수치를 발열 감소율로 해석하지 않는다. 너무 잘게 분할해 작업량이 증가한 중간 실험은 보존하고 최종 구현에서 제외했다.
- 개인방 연못 표본의 그리기 호출은 약 137→84.5회. 연못→야경→한강→단풍→설경→연못에서 메시 87→139→152→104→107→87, 퇴장 후 장면 수 1개로 복구했다.

원시 자료는 `evidence/mobile-optimization/`에 있다. `workload/`, `tuned-workload/`는 중간 조정 자료이며 최종 구역 분할의 부하 자료는 `site-workload/`, 최종 통합 검사는 `final-integration/`, 연속 검사는 `final-soak/`다.

## 검증 한계

### 심한 발열 재신고에 따른 공개 v58 부하 재검사

사용자의 실제 iPhone 발열 재신고를 해결 판정보다 우선한다. 이번에는 제품 코드·공개 배포를 바꾸지 않고 공개판을 Mac WebKit의 모바일 조건으로 다시 측정했다. 기본 가벼움·20fps, 렌더 크기 280×471이었다. 낮 중앙마당 약 560회, 밤 약 570회 그리기 호출로, 낮/밤 모두 프레임당 약 1,220만~1,269만 인덱스가 처리됐다. 방문객의 렌더링·행동을 검사 브라우저에서만 잠시 제외하면 약 407/417회로 줄었고 인덱스 감소는 작았다. 따라서 방문객은 호출 부담의 일부이며 정적 장면 복잡도도 별도 개선할 필요가 있다. 이는 전력·온도 기여율 측정이 아니다.

공개판에서 5초 표본을 각각 측정했다. 입장 직후 100프레임, 45초 이상 무입력 후 75프레임, 지도 열림 0프레임, 명상 중 101프레임으로 20→15→중지→20fps 정책이 실제 동작했다. 요청 실패는 0개였고 기존 WebSocket 생성자 fallback 진단 2개가 별도 관찰됐다. 무입력 상태도 계속 15fps로 그리므로 정지 화면의 부하가 사라진 것은 아니다. 자동 조절은 지속적인 프레임 지연을 기준으로 하며 기기 온도·전력에 반응하지 않으므로, 부드럽게 실행되면서 뜨거워지는 상황을 감지하지 못한다.

추가 후보는 모바일에서 먼 정적 건물·장식의 실제 모델 단순화, 원거리 방문객의 표시 부품 통합, 정지 상태 갱신 빈도의 추가 절감이다. PC 품질 유지가 조건이다. 실기기 원인 확정을 위한 Safari 측정과 사용자의 발열 발생 시점 확인이 남아 있다. 기본 20fps 정상 실행을 발열 해결로 판정하지 않는다. 자료는 `evidence/mobile-heat-followup/`에 있다. states의 topMeshes는 SmartArray 내부 버퍼 전체를 읽은 진단용 표본이므로 가시 모델 순위나 결론의 근거로 사용하지 않았다.

실제 iPhone 14 Pro의 기기 온도나 iOS Safari의 강제 종료는 측정하지 못했다. 모바일 에뮬레이션 통과를 실기기 발열 해결로 판정하지 않는다. WebKit의 기존 Colyseus 생성자 fallback 진단은 `sdkDiagnostics`로 별도 보존한다. 실제 기기에서 입장·지도 반복·5분 이상 사용 후 온도와 재로딩을 확인해야 한다.

## 공개 체험판 확인

58버전 배포 성공. 공개 주소에서 Chrome 모바일 통합 검사와 WebKit 단독 재검사 모두 통과했다. 최초 병렬 검사 중 WebKit 한 번은 언어 버튼이 나타나지 않는 빈 화면에서 25초 대기 제한에 걸렸다. 이때 페이지 오류는 없었고 원인은 확정하지 못했다. 실패 자료를 보존하며 재검사 통과로 이 실패를 지우지 않는다.

이후 공개 WebKit 연속 입장 3회도 통과했다. 첫 입장 버튼부터 장면 준비까지 약 4.08초였으며 입장 전 3D 생성 없음, 입장 후 20fps를 확인했다. 실제 휴대폰 로딩 시간 보장은 아니다.

공개 주소의 독립된 Chrome 브라우저 3개가 같은 Colyseus 채널에 참가했고 각자 상대 2명과 가상 방문객 17명을 확인했다. 이동·12지신 외형·법복·참배 전파, 개인방 비공개와 복귀, 오프라인 제거·재접속 검사 모두 통과했다. 3명 참가자 평가가 아닌 자동화된 독립 브라우저 세션 검수다.
